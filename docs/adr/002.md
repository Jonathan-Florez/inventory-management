# ADR-002: Schemas Pydantic organizados por feature, no por entidad

## Contexto
schemas/ necesita una convención de organización. Dos opciones naturales:
un archivo por entidad de dominio (user.py, category.py...) calcado de
models/, o un archivo por feature/router (auth.py, categories.py...).

## Decisión
Un archivo de schemas por feature, espejando routers/: schemas/auth.py,
schemas/category.py, schemas/product.py, etc. Un schema compartido y
genérico (PaginatedResponse[T]) vive en schemas/common.py`.

## Alternativas consideradas
- **Un archivo por entidad, calcado de models/: los modelos representan
  tablas (una entidad, una tabla, un archivo tiene sentido ahí). Los schemas
  representan contratos de API por operación — un mismo endpoint necesita
  varios schemas (Create/Update/Read) que no siempre mapean 1:1 a una tabla.
  Forzar el mismo criterio en ambas capas fragmenta innecesariamente.

## Consecuencias
- Cualquiera que abra routers/categories.py sabe que sus schemas están en
  schemas/category.py sin tener que buscar.
- PaginatedResponse[T] genérico evita duplicar la misma estructura de
  paginación en cada feature.

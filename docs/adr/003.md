# ADR-003: ON DELETE CASCADE para categoría → productos → movimientos

## Contexto
El PDF no especifica qué debe pasar al borrar una categoría con productos
asociados. Había que decidir: bloquear el borrado, dejar productos huérfanos,
o borrar en cascada. Se decidió cascada

## Decisión
product.category_id y movement.product_id tienen ON DELETE CASCADE a
nivel de base de datos (no lógica manual en el service). Borrar una
categoría borra automáticamente sus productos, y borrar un producto borra
automáticamente sus movimientos.

## Alternativas consideradas
- Cascada manual en el service (borrar movimientos, luego productos,
  luego categoría, en una transacción Python): funciona, pero es fácil de
  olvidar mantener sincronizado si se agregan nuevas entidades relacionadas
  en el futuro. La responsabilidad quedaría dispersa en código de aplicación
  en vez de garantizada por el motor de base de datos.
- Bloquear el borrado si hay productos asociados: más conservador, pero
  no es lo que se decidió como comportamiento deseado para este proyecto

## Consecuencias
- Atomicidad garantizada por Postgres: un solo DELETE dispara toda la
  cascada, sin riesgo de estados intermedios inconsistentes.
- El service de categorías no necesita lógica de borrado en cascada —
  se reduce a validar existencia/propiedad y delegar el DELETE.
- Riesgo aceptado: borrar una categoría es una operación destructiva e
  irreversible
